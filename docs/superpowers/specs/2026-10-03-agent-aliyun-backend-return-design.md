# 新版 PSKit 后端迁回阿里云的部署设计

## 目标与当前事实

用户决定让阿里云运行新版 Python/Pi 后端，A6000 专门运行 AF3。React 构建产物继续由阿里云宿主机 Nginx 提供；Supabase 和 LiteLLM 也留在阿里云。A6000 的 AF3 接收器继续主动领任务、回报进度和上传产物，经 WireGuard 连接阿里云私网地址 `10.9.8.1`。用户明确选择沿用这种通信方式；阿里云无需新增到 `10.9.8.2` 的 AF3 推送接口。旧 `pskit.bioailab.net` 和旧 PSKit 容器不参与迁移。

本设计取代 [A6000 后端迁移设计](2026-10-02-agent-a6000-backend-migration-design.md) 的**最终运行位置**，并恢复 [阿里云独立部署设计](2026-10-02-agent-cloud-docker-deployment-design.md) 中的云端后端 + A6000 主动领任务拓扑。现有真实用户、Agent 会话、Pi 会话和 AF3 任务状态必须保留，切换期间始终只有一个新版后端写 Agent 数据。

截至 2026-10-03 的只读核对：阿里云运行独立 Supabase、LiteLLM、React 静态站，旧 `pskit-agent-cloud_agent_data` 卷仍存在但不是最新数据；A6000 运行 `pskit-agent-a6000-backend-1`、本机 AF3 回调代理和接收器。A6000 Agent 数据库 `quick_check=ok`，Run 状态为 `completed=9, failed=1`，AF3 job 表和接收器 journal 均为空。这个空闲结论只代表检查时刻，正式切换前必须重新核对。

## 方案选择

1. **采用：云端后端 + A6000 主动领任务。** 复用已有 AF3 租约、回调鉴权、持久 journal/spool 与自动唤醒机制。前端到后端、后端到 Supabase/LiteLLM 都留在阿里云，只有 AF3 控制和产物跨 WireGuard。
2. **备选：云端主动向 A6000 推送任务。** 需要在 `10.9.8.2` 开放新入站 API，并重新处理提交 ACK、幂等、重试和长任务结果，增加两套任务状态。本次不采用。
3. **维持 A6000 后端。** 不满足用户希望将后端放在阿里云的目标，本次不采用。

## 目标拓扑

```text
浏览器 ─HTTPS─> 阿里云 Nginx agent.bioailab.net
                  ├─ /、静态资源 ─> 本机 React dist
                  ├─ /api/v1/* ─> 127.0.0.1:18088 ─> 新版 Python/Pi
                  └─ 既有 OAuth 授权/回调 ─> 本机 Supabase 网关

阿里云新版 Python/Pi ─本机 Docker 网络─> Supabase
                    └─私网 10.9.8.1:4000─> LiteLLM
                    └─独立持久卷─> Agent SQLite + Pi 会话

A6000 AF3 接收器 ─WireGuard─> 10.9.8.1:18184 (仅允许 10.9.8.2)
                                  └─127.0.0.1:18185─> 受限回调代理
                                                           └─Docker 网络─> Python 后端
A6000 AF3 计算容器 ─持久 spool/journal─> 接收器
```

阿里云后端以固定镜像标签运行，只发布回环 `127.0.0.1:18088`，不开放公网 Docker 端口。Nginx 的 `/api/v1/` 上游从 `10.9.8.2:18088` 改为本机，保留 SSE、文件上传、同域 Cookie 与 `/internal/` 拒绝规则。React `dist`、证书和 Supabase OAuth 精确路径保持现状。AF3 私网入口恢复原先的 `10.9.8.1:18184` 监听，仅允许 `10.9.8.2`，转发到回环的专用代理；该代理只允许 AF3 领取、租约续期、进度、结果和产物路径，并校验回调密钥、worker ID，后端继续校验任务归属与租约。私网端口不能作为公开 API。

云端后端沿用现有 `claude-opus-4-8` 模型别名和 LiteLLM 服务端虚拟 key；LiteLLM 团队及用户预算和 PSKit Token/GPU 配额不因搬迁重置。模型 key、Supabase key 与 AF3 回调密钥只放受限环境文件，不进入镜像、Git、浏览器或终端输出。A6000 接收器继续使用同一 worker ID、现有镜像、spool/journal 和计算容器；只把回调目标从本机 `127.0.0.1:18185` 改为阿里云 `http://10.9.8.1:18184`。不创建第二个接收器或计算容器。

## 数据所有权与迁移

最新 Agent 数据只在 A6000 的 `pskit-agent-a6000_agent_data` 卷：`agent.sqlite3`（含已提交 WAL）和 `pi-sessions/`。用户账号、身份、邮件和 Storage 数据已经位于阿里云 Supabase，不搬迁。现存阿里云 `pskit-agent-cloud_agent_data` 是迁出前的旧副本，**不能启动旧后端继续写入，也不能用它覆盖 A6000 的更新**。

先为旧云端卷留只读备份，再将 A6000 当前卷用仓库已有 `agent_data_snapshot.py` 制成 SQLite 一致性快照和 Pi 文件清单，经 SSH 传到阿里云并校验整体与逐文件 SHA-256、SQLite 完整性。恢复到**新的空 Agent 卷**，使旧卷原样保留以便审计；不使用 `docker compose down -v`。目标卷文件所有权需匹配后端容器 UID/GID。只有在 A6000 后端和接收器停止领任务、确认无运行中 Run、AF3 claim 或未 ACK journal 后才获取最终快照。切换期间绝不同时运行两个指向不同 Agent 卷的生产后端。

## 切换顺序

1. **准备但不接管。** 固定并传输当前后端镜像到阿里云；准备云端后端与 AF3 回调代理 Compose 覆盖文件、受限环境文件、新空数据卷及本机 Nginx 配置。核对 Supabase、LiteLLM、WireGuard、镜像标签、磁盘空间和配置渲染。先验证私网入口配置及无密钥拒绝，但不启动第二个生产后端。准备可回退的 root Nginx 安装脚本；云端 `ecs-user` 无 sudo，因此主机 Nginx 的最终 reload 由用户在 root 会话运行脚本。
2. **冻结写入与取快照。** 再次检查 Run/AF3 job、接收器 journal/spool 和计算容器；有未完成工作则等待或对账，不强行切换。停 A6000 接收器，再停新版 A6000 后端及回调代理，保留计算容器和旧 PSKit。备份旧云端卷、快照 A6000 当前卷、校验并恢复到云端新卷。源卷和归档均不删除。
3. **云端私网验收。** 只启动云端新版后端与 AF3 回调代理，验证 readiness、既有账号、项目/会话/Pi 历史、文件、Token/GPU 余额、LiteLLM 实际模型调用及无密钥的 AF3 入口拒绝。恢复 `10.9.8.1:18184` 私网入口后，只启动一个 A6000 接收器并确认它能读取其 owned-jobs；计算容器不重建。受控 AF3 任务应证明领取、进度、结果、产物、ACK、配额结算和 Pi 自动唤醒。普通用户 GPU 每日额度维持现值，验收账号如需临时额度，验收后恢复。
4. **公网切流量。** 备份当前 `agent.bioailab.net` Nginx 配置，修改 `/api/v1/` 上游为 `127.0.0.1:18088`；`nginx -t` 和 reload 成功后检查公网登录、会话、SSE、上传、Cookie、`/internal/` 拒绝及旧站。最后停 A6000 新版 API 代理；A6000 只保留 AF3 接收器、计算容器和旧站所需容器。
5. **收尾。** 记录镜像、数据快照校验、切换时刻、私网端口和回退命令。旧 A6000 Agent 卷与云端旧卷保留到观察期结束；不把历史备份当作在线数据。

切换过程中网页静态资源继续可用，API 在冻结和数据传输期间会短暂不可用。先完成私网验收再改公网路由，可以缩短公网 502 时间，但不会让两个后端同时写入。

## 故障与回退

- 云端后端启动前失败：A6000 原卷尚未迁出写入；在确认接收器 journal 与任务状态一致后，可恢复 A6000 后端和本地回调代理，公网 Nginx 无需切换。
- 云端后端启动后、产生任何新写入前失败：停云端后端，恢复 A6000 原配置，重启接收器；源卷仍在 A6000。
- 云端产生新会话、任务或回调后失败：先停云端入口、接收器及后端，对账任务与 journal；必须把**云端最新** Agent 数据一致性快照迁回 A6000，再恢复 A6000 后端和本机回调路径。不能直接启动 A6000 旧卷，否则会丢会话、余额和任务结果。Nginx 回退也必须与数据所有权切换同步。
- WireGuard 中断：网页、登录和普通聊天仍在阿里云可用；AF3 接收器暂停领任务或在本地 journal/spool 保留未 ACK 结果，连接恢复后按原任务 ID 续传。任务租约过期和重试由现有后端规则处理，不另建消息队列。
- Supabase 或 LiteLLM 故障：后端明确报告依赖异常，不切到另一套身份库或未计费模型。GPU 任务的取消和单产物 20 MiB 上限仍是独立的产品限制，不因迁移改变。

## 完成标准

`agent.bioailab.net` 的静态页与 `/api/v1/` 都由阿里云提供，阿里云能看到唯一运行中的新版 Python/Pi 后端及正确的最新 Agent 卷；A6000 只为新版保留一个 AF3 接收器和计算容器。既有 Supabase 账号、Agent 历史、Pi 会话、上传文件、配额均可用；真实模型调用经过 LiteLLM；AF3 经 WireGuard 成功领任务、回传产物并唤醒 Agent。无 AF3 私网密钥的请求被拒绝，公网 `/internal/` 不可达，旧 `pskit.bioailab.net` 保持可用。所有验证基于实际响应、数据状态及任务记录，不把 Mock 结果当成真实 AF3。
