# 新版 PSKit 后端迁至 A6000 的部署设计

## 2026-10-02 前端部署修订

用户随后明确选择阿里云宿主机 Nginx 直接服务 Vite `dist`，不再保留常驻 Web 容器。以下原设计中“阿里云 Web 容器”“`127.0.0.1:18085`”是修订前拓扑；最终公网 Nginx 的 `root` 为 `/var/www/agent.bioailab.net`，`location /` 用 SPA `try_files`，`/api/v1/` 仍经 WireGuard 到 A6000，两个 OAuth 授权/回调精确路径直接代理本机 Supabase Envoy `127.0.0.1:18130`。已有固定版前端容器只作为提取其已构建 `dist` 的来源，验收后停止。独立静态 Web 配置保留作备用验证，不是最终运行服务。

## 目标与已确认的边界

用户希望在 A6000 上看到并运行**新版** PSKit 的 Python 后端、Pi Agent 和 AF3 计算，而不是仅有 AF3 接收器。`new_frontend`、Supabase、`agent.bioailab.net` 的 DNS、证书及公网 HTTPS 入口留在阿里云。旧 `pskit.bioailab.net` 与 A6000 上的旧 PSKit 容器继续运行。新版已创建的 Supabase 账号、Storage 数据、Agent 会话和 Pi 会话需要保留；切换后只能有一个新版后端处理请求和后台任务。

这是对 [云端独立部署设计](2026-10-02-agent-cloud-docker-deployment-design.md) 的**运行位置修订**。原设计中“新版 Python/Pi 后端运行在阿里云”被本设计取代；其独立 Supabase、旧站隔离、固定镜像版本、回调鉴权和持久化要求继续适用。

## 当前可核对的状态

- 阿里云 `47.121.29.141` / WireGuard `10.9.8.1` 上，新版前端、后端、AF3 回调代理、模型替身和固定版本 Supabase 已分别以独立 Compose 项目运行。`https://agent.bioailab.net/login` 的证书校验和 HTTP 200 已通过；邮箱注册仍关闭，模型网关仍是测试替身。
- A6000 WireGuard 地址为 `10.9.8.2`。旧 `pskit2-v020-smoke-*` 与新版 `pskit-af3-receiver-cloud-20261002`、`pskit-af3-compute-real-test-20261002` 同时存在。新版 Python/Pi 后端目前**不在** A6000。`10.9.8.2:18088` 未占用；A6000 无宿主机 Nginx，Docker Compose 可用，`/data` 与 `/data1` 仍有空间。
- 阿里云 Supabase Envoy 只发布到 `127.0.0.1:18130`；Agent SQLite 与 Pi 会话位于 `pskit-agent-cloud_agent_data` 持久卷。现有 A6000 接收器经 WireGuard 访问阿里云 `10.9.8.1:18184`。这些地址和卷不是迁移后的最终拓扑。

## 方案比较

1. **阿里云保留入口与 Supabase，A6000 运行新版后端和 AF3（采用）。** 满足用户选择；账号与 Storage 不迁库，后端与 GPU 同机。代价是登录、数据访问和浏览器 API 都依赖 WireGuard，必须设计私网代理与断线回退。
2. **整套新版都迁 A6000。** 减少后端到数据库的网络往返，但违背“前端仍在阿里云”的选择，还要迁移 Supabase 数据并重新设计公网入口。
3. **沿用阿里云后端，仅把 AF3 留 A6000。** 是当前状态，无法满足“新版 PSKit 后端在 A6000”的要求。

## 目标拓扑与接口

```text
浏览器 ─HTTPS─> 阿里云 Nginx agent.bioailab.net
                  ├─ / 与静态资源 ─> 127.0.0.1:18085 ─> React Web
                  ├─ /api/v1/* ─WireGuard─> 10.9.8.2:18088 ─> 私网 API 代理
                  │                                         └─ Docker 内网 ─> Python/Pi 后端
                  └─ 仅既有 OAuth 授权/回调路径 ─> 阿里云 Supabase

A6000 Python 后端 ─WireGuard─> 10.9.8.1:18130 ─> 私网 Supabase 代理
                                               └─127.0.0.1:18130─> Envoy/Auth/Storage

A6000 AF3 接收器（现有 host 网络）─127.0.0.1:18185─> AF3 回调代理
                                                  └─Docker 私网─> Python 后端
A6000 AF3 计算容器 ─持久 spool─> AF3 接收器
```

阿里云宿主机 Nginx 的 `/api/v1/` 路由直接转发到 A6000 的私网 API 代理，其余页面仍由本机 Web 容器提供。同域请求保持现有浏览器 API 地址和 `Secure`/`HttpOnly` Cookie 语义；SSE 关闭响应缓冲，文件上传关闭请求缓冲，并沿用 25 MiB 限制及长请求超时。`/internal/` 不进入公共 API 路由，仍返回 404。旧站的域名、证书与虚拟主机不改。

A6000 没有宿主机 Nginx，因此用独立的轻量代理容器使用 **host 网络**监听 `10.9.8.2:18088`，在代理层只接受 `10.9.8.1`，再转给后端映射在本机回环的 `127.0.0.1:18089`。后端本身不发布到 A6000 公网、校园网或旧 PSKit 端口。API 代理不使用 Docker 的 WireGuard 端口发布；代理来源限制和宿主机防火墙同时保护该入口。云端对 Supabase 的私网代理监听 `10.9.8.1:18130`，只接受 `10.9.8.2` 并转至现有回环 Envoy；Supabase Studio、数据库端口和密钥不对 A6000 以外的来源开放。

云端 Web 镜像需要一个仅服务静态文件和现有 OAuth 路径的配置，移除启动时对 `backend:8000` 的 Docker DNS 依赖；Compose 也需改为可独立启动 Web。云端停止旧版**新版后端**后，Web 仍须能独立重启。A6000 的后端使用独立 Compose 项目、固定镜像标签与持久卷；通过有外连能力的容器网络访问 `10.9.8.1:18130`。公开 URL 仍为 `https://agent.bioailab.net`，内部 `SUPABASE_URL` 改为私网入口，浏览器不接触私网地址。

AF3 接收器保留现有 host 网络和持久 spool/journal，只把回调目标改为本机 `127.0.0.1:18185`；回调代理在回环地址发布端口，再通过 Docker 私网连接后端。后端和代理仍校验同一 worker 身份、回调密钥、租约与任务归属。原阿里云 `10.9.8.1:18184` 回调入口在切换成功后停用，不再维持两条有效回调链。计算容器不重建，运行中任务不因入口切换而丢失。

## 数据迁移与切换顺序

1. **准备，不切流量。** 在 A6000 准备新版后端、模型测试替身和私网 API 代理所需的镜像与配置；阿里云建立仅供 A6000 使用的 Supabase 私网入口。凭据只存权限 `0600` 的文件或受限卷，不打印、不提交。先从 A6000 对私网网关做连通性与拒绝未授权请求检查；此时**不启动接管真实会话或 AF3 任务的第二个生产后端**。
2. **冻结单一写入者。** 检查新版 Run、AF3 claim、接收器 journal 与 spool，无进行中的任务再开始切换；暂停对外 API 写入并停止阿里云新版后端及旧 AF3 回调代理。保留阿里云 Supabase、Web 和旧 PSKit。对 Agent SQLite、WAL 与 Pi 会话目录做一致性备份，迁到 A6000 持久卷并校验文件与数据库；Supabase 的账号和 Storage 原地保留。
3. **私网恢复。** 在 A6000 启动**唯一**新版后端，再将现有 AF3 接收器接到本机回调代理。先在私网验证健康、既有账号、项目、会话、Pi 历史、SSE、上传、任务状态与额度；AF3 使用可控的小任务验证完成回调、ACK、持久化和唤醒。模型替身的结果明确标记为测试，不视为真实模型联通。
4. **公网切流量。** 阿里云先保存新站 Nginx 配置，再增加 `/api/v1/` 到 `10.9.8.2:18088` 的路由；`nginx -t` 成功后 reload。检查公网登录、刷新 Cookie、聊天流、上传、`/internal/` 拒绝和旧站可用性。云端 Web 使用静态独立 Compose 配置，云端旧后端保持停止。
5. **收尾。** 确认 A6000 后端持久卷和接收器 journal 可跨容器重启恢复，记录镜像版本、私网端口、备份与回退命令。真实模型网关、SMTP/注册及 Google OAuth 的缺口继续单独跟踪，不因后端迁移而宣称已完成。

## 故障与回退边界

- 切流量前失败：保留阿里云原部署与数据，删除或停止 A6000 新容器即可；旧站不受影响。
- 切流量后 WireGuard 或 A6000 故障：页面静态资源可由阿里云提供，但聊天、登录 API 和任务状态不可用。先恢复私网或回退 API 路由；**不能**仅重新启动阿里云旧后端，因为 A6000 期间已有新的 SQLite/Pi/AF3 状态。需要冻结 A6000 写入、对账并把最新 Agent 数据反向迁移后，才能由云端后端接管。
- 接收器或计算容器故障：保留其持久 spool/journal 与后端任务租约，按原任务 ID 恢复；不能在两地同时领取同一任务。AF3 运行中任务取消和 20 MiB 单件产物限制仍是现有未解决约束。
- 阿里云 Supabase、WireGuard 或私网代理不可用时，A6000 后端不得降级到另一套身份库；健康检查和错误响应要明确反映依赖失败。公网入口与私网端口均不能绕开用户身份、配额和回调鉴权。

## 验收界限

完成条件是：`agent.bioailab.net` 仍从阿里云提供 React 页面，所有新版 `/api/v1/` 请求实际到达 A6000 的 Python/Pi；A6000 上能看到独立新版后端容器及 AF3 接收器/计算容器；既有测试账号和 Agent 历史可用，Supabase 数据仍在阿里云；SSE、上传、配额、AF3 回调和自动唤醒在新拓扑下通过；旧 `pskit.bioailab.net` 仍可访问。每一步记录端到端证据，不把测试替身当真实模型或真实 AF3 结果。
