# A6000 通用 MCP 接收器与 CORAL 生产恢复

## 已确认的边界

延续已批准的通用计算、配置驱动 Tool Product 计划。用户进一步明确：接收器统一运行在 A6000；AF3 接收器也合并进通用 MCP 接收器。阿里云继续运行前后端、Pi、认证、数据库与调度；4090 提供 CORAL MCP 模型服务。

## 实现

- A6000 一个容器、一个 Python 进程，运行通用 MCP 与 AF3 两个接收循环。两者复用 `Receiver`、持久 Journal、回执验证机制，各自使用独立 journal 文件。
- CORAL 使用服务器下发的不可变 MCP binding，调用 4090 已审核的四项能力。阿里云新增仅在 WireGuard 上监听的通用回调入口；后端继续验证服务密钥及任务租约。
- AF3 在同一进程内提供仅绑定 `127.0.0.1` 的 `af3.submit` / `af3.status` MCP。提交以服务端 UUID 为幂等键，通过文件锁校验并持久化输入。既有 AF3 模型计算容器继续读取共享 spool，独立于接收器生命周期。
- `Af3ControlClient` 将既有 AF3 HTTP claim、heartbeat、artifact、result 协议转换为通用执行 grant 与回执。保留历史任务、额度、产物及会话唤醒语义。此处属于兼容边界，尚未把历史 AF3 全量迁入通用服务注册表。
- 模型结果先写入接收器 outbox；验证服务端已提交的回执后删除 journal 记录，再清理 AF3 spool。网络中断、回执丢失不删除结果，不重复运行模型。
- 已开始的 AF3 被取消或超时后，仅继续观察既有计算，不授权新提交。原租约凭据用于回传晚到用量；确认服务端 `reconciled` 后才清理记录，不把模型完成误写为用户任务成功。
- 仅具备持久输入幂等能力的 AF3 适配器允许恢复中断提交。其他 MCP immediate 调用发生不确定崩溃时保持 `unknown`，等待人工核对，不能盲目重复计算。
- 合并进程内隔离服务故障：CORAL 需要人工核对时不停止 AF3 的心跳与结算；两者都保留各自的 journal。
- AF3 旧计算器仅报告取整 GPU 分钟。映射为 `gpu_device_ms` 时标为 `estimated`；缺失的 CPU 和 wall 耗时保持空值。不得宣称 CUDA 计时或补造数据。

## 执行与验收

1. 恢复 CORAL 提供者的同机 Redis 认证与隔离依赖，执行四个真实验收案例；全部通过后以审计记录发布生产 Tool Product。
2. 用既有合成账号验证公开目录、四种 UI 模式、正常提交、A6000 领取、4090 执行、用量结算及产物。临时有上限的测试额度用后恢复；其他用户额度保持原值。
3. TDD 验证重复提交、进程重启、丢失回执、真正 Streamable HTTP MCP 通信、双接收循环，以及与既有 AF3 API 的重复产物上传和幂等结果提交。
4. 制作可追溯的不可变接收器源码制品，核对固定运行镜像依赖，并用隔离容器执行 MCP smoke。
5. 核对两类接收器 journal 与后台活动任务。安全停止旧 AF3 接收器，保留模型计算容器及所有持久文件；启动统一容器并验证双循环。
6. 真实 AF3 小输入验收任务领取、完成、产物上传、额度结算和 spool 回执后清理；记录制品、运行容器和可逆恢复步骤。

## 恢复

合并失败时先核对通用 AF3 journal 与服务端 owned jobs。不要同时启动两个 AF3 接收器；不要删除持久卷或已有结果。只有确认可安全交回旧协议时才恢复旧 AF3 接收器。CORAL 接收循环可恢复到其先前制品。已结算任务和用户历史保留。
